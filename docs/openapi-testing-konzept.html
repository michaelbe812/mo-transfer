Generierte Testing-Libs im Slice-Konzept

Wie passen generate-api-testing, die generierte Baseline und die Slice-Testing-Libs zusammen? Stand: feat/testing-mocks-ohne-faker, settings.testing.mocks: "examples".

Kurzantwort 1 · Schichten 2 · Testdaten (entschieden) 3 · Task-Pipeline 4 · Outcomes 5 · Ort konfigurieren Offene Fragen
Kurzantwort
  • Drei Schichten: generierte Client-Testing-Lib (Vertrag + Baseline) → Slice-Testing-Lib (Fixtures, kuratierte Handler, Szenarien) → Specs.
  • Entschieden: keine generierten Testdaten, kein faker. Die generierte Lib liefert Vertrag (<client>Http) + Baseline (<client>Handlers); Testdaten sind handgeschriebene Fixtures der Slice-Testing-Lib (a<Dto>()), die der shared Clients in shared/testing (aNotification()).
  • Baseline-Bodies werden beim Generieren aus Spec-examples berechnet (sonst feste Platzhalter) – kein Zufall, byte-gleich pro Spec, vom Typecheck gegen die Spec geprüft.
  • Grund: generierte Fake-Daten nutzte keine Fixture, wenig Wert. Handler bleiben, weil sie mit der Spec synchron bleiben („jede Operation antwortet“).
  • Pipeline: derselbe Runner wie für den Client, Preset testing. Unabhängig vom Adapter, nur aus der Spec. Ergebnis landet gitignored in <client>/testing/src/generated/.
  • Den Ort steuern Client-Schlüssel + settings.libsDir / clientFolder / outputDir / aliasPrefix / sharedScope. Der Teilordner testing ist fest.

2 · Testdaten: entschieden

Früher (schema-faker) lieferte die generierte Lib zusätzlich Fake-Daten (get<Op>ResponseMock, faker, mock-runtime.ts) – zweite Datenquelle neben den Fixtures. Optionen waren A behalten, B rausnehmen, C Schema-Factories. Gewählt: Baseline behalten, Fake-Daten raus (Engine examples).

Wert-Reihenfolge der Baseline

Media-example(s) → Schema-example/examples[0] → const → default → enum[0] → erste oneOf/anyOf-Variante (Discriminator) → Platzhalter: date 2026-01-01, date-time 2026-01-01T00:00:00.000Z, uuid Null-UUID, email user@example.com, uri https://example.com, string = Property-Name, Zahl = untere Grenze sonst 0, boolean false. Objekte: required + optionale mit Example. Arrays: max(minItems, 1). Nur lokale $refs. Lesbare Daten → example an jedes Property der eigenen Specs.

3 · Task-Pipeline der Testing-Lib

Phase 1 · Gerüst (einmalig, committet) – Generator client

nx g @mo-transfer/tooling-openapi:client booking-client --domain=booking --spec=… [--no-testing]

  • Eintrag in openapi-clients.json (ohne pipeline.testing: false → Testing-Lib)
  • <client>/testing/project.json: Name booking-generated-booking-client-testing, Tags scope:booking type:testing feat:none generated, implicitDependencies → Client-Projekt, lint/typecheck mit dependsOn: [generate-api-testing, ^generate-api-client, ^generate-api-testing]
  • testing/src/index.ts = export * from './generated'; (Pflicht – sonst bricht die Pipeline in generate ab)
  • tsconfig + paths-Alias über settings.scaffold; Hinweis nennt <client>Handlers (examples) bzw. nur <client>Http (none)

Phase 2 · Auslösung – Nx

nx test booking-state └─ dependsOn ^generate-api-testing (targetDefaults, transitiv über den Graph) └─ booking-generated-booking-client-testing:generate-api-testing ← inferiert vom Crystal-Plugin (createNodes) executor @mo-transfer/tooling-openapi:generate-testing options { client: "booking/generated/booking-client" } └─ facade.generateTesting → resolveClient (liest openapi-clients.json zur Laufzeit) → runPipeline(testingPreset(mocks))

Gecacht. Cache-Hit → Outputs src/generated werden nur wiederhergestellt.

Phase 3 · Runner, Preset testing (dieselben Stages wie der Client)

specOverlays (nur mit Feature-Flag) → tmp/openapi/<pfad>/testing/
generatePrüft src/index.ts; servers[0].url; openapi-typescript → schema.ts; http.ts; Engine examples → handlers.ts
classifyalle Dateien → Teil testing, sortiert
transform[]pipeline.transforms, ctx.preset = 'testing'
splitläuft, ändert nichts (nur ein Teil)
barrelaus (barrel: false), index.ts kommt vom Preset
finalizeprettier (pipeline.format) + Header „Do not edit, do not commit“
writeersetzt testing/src/<outputDir>/ komplett

Unabhängig vom Code-Adapter (openapi-tools, hey-api …): das Testing-Preset liest nur die Spec. Fehler tragen die Phase (OpenApiError, --verbose streamt). Ausgabe deterministisch.

5 · Ort konfigurieren

Pfad der Testing-Lib (partRoot in settings.ts):

StellschraubeDefaultWirkung auf die Testing-Lib

settings.scaffoldeingebautproject.json/tsconfig/Tags der Lib (hier tooling-conventions/openapi-scaffold)
pipeline.testing: false / --no-testingankeine Testing-Lib, kein generate-api-testing
pipeline.testing.mocks / settings.testing.mocksnoneInhalt, nicht Ort (s. Abschnitt 3)
Plugin-Option testingTargetName (nx.json)generate-api-testingTarget-Name, nicht Ort
fest–Teilordner testing, Tags type:testing feat:none generated, tmp-Pfad tmp/openapi/<pfad>. Pfade werden validiert (bleiben im Workspace)

Bewusst nicht möglich: die Testing-Lib in die Slice-Testing-Lib legen (z.B. libs/booking/testing/src/generated). Gründe: ein Projekt = ein Generator-Output (Cache, write ersetzt den Ordner komplett), eigene Tags generated, Boundaries.
